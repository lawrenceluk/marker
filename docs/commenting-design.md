# Commenting prototype

Recommendation: add quote-anchored threads to the existing reader, with a phone-sized sheet and a revision-checked API. Keep the raw Markdown editor. This is a prototype for review, not a production rollout.

## Anchors and editing

Store the selected raw Markdown as `exact`, 48 UTF-16 code units of `prefix`/`suffix`, and a source `position:{start,end}`. This retains the [W3C-inspired text quote](https://www.w3.org/TR/annotation-model/#text-quote-selector) fallback but gives repeated passages their own source positions. Rendered text leaves carry parser-derived source offsets; selections spanning bold or links include intervening Markdown syntax. New composers show the actual rendered selection, and existing thread quote labels strip Markdown for display. Stored quotes and source offsets remain raw. Partial selections through decoded entities/escapes and fenced code without parser positions are still unsupported; select surrounding text instead.

Every content-changing write maps stored ranges through a server-side old→new character diff before committing. A range wholly preserved by the diff is shifted and verified against the exact quote; insertion/deletion inside it marks the anchor Outdated (`position:null`) rather than jumping to another matching phrase. Outdated stays explicit on subsequent writes. Threads without offsets or with unusable offsets, and diff computation failures, retain exact/prefix/suffix lookup as a fallback. Successful legacy lookup acquires offsets during the next content write. Mapping applies to overwrite, append, prepend, old content-only clients, raw-editor saves and atomic content-plus-operations requests.

Use [jsdiff](https://github.com/kpdecker/jsdiff)'s Myers-based `diffChars` on the server, bounded to 50 ms / 2,048 edits. It handles Unicode code points; mapping uses change-string lengths for UTF-16 offsets. Known append/prepend operations supply exact insertion diffs, avoiding ambiguity when identical passages are inserted at either end. `diff` 9 has no runtime dependencies; a standalone measurement bundle of the mapper plus diff code is 4,852 bytes minified / 2,035 bytes gzipped, and it is not imported by client components. This keeps a maintained diff algorithm out of the browser and avoids maintaining a custom diff engine. The previous quote-only approach remains the bounded-work fallback. Snapshot diffs still cannot infer author intent among indistinguishable edits/moves of identical text without an edit-operation history.


## Storage and concurrency

Use a separate JSON `comments` field in the existing `note:{key}` hash, with a maximum 100 threads, 100 messages per thread, 4,000 characters per message, 8,000 per quote and 256 KiB total comments. This is logically separate from content but physically shares its lifecycle: existing Lua writes preserve the field, rename moves it, TTL changes apply to it, expiry/delete remove it. No independent Redis key or migration is needed. Content keeps its 1 MiB limit.

A shared `rev` increments for every successful content or comments mutation. Every write now reads a snapshot and commits content plus mapped comments in one Lua compare-and-swap checking existence, revision, previous source and previous comments. Diffing occurs before the CAS; a competing write invalidates the entire computation, so no stale map can commit and there is no intermediate state with new content and old anchors. `if_rev` callers get 409 on a race. Old unconditional clients reread/rediff/recompose and retry up to eight times, returning 409 under sustained contention. In particular, two unconditional appends/prepends retain both edits. Rename and TTL remain inside the existing Redis hash lifecycle; legacy migration retains its remaining TTL.

Comments require `if_rev`, and an optional content edit plus all comment operations commit atomically. Shared revision checks conservatively make unrelated replies conflict with content edits. Timestamps and IDs are server-generated. There is no history or exactly-once retry token: after a network timeout, reread to determine whether the action committed.

## Roles and visibility

Lawrence's decision: exactly two labels. Browser cookie requests are `You`; explicit-key API requests are `Agent`. No names or role picker. These labels describe the request path and cannot prove a human/agent identity. Any bearer-key holder can use either request path and can read, reply, edit, resolve or reopen. Persist links still grant full access. Comments load automatically in view mode after hydration; they are never serialized into initial page HTML or included in metadata, OG images or preview snippets. This is presentation hiding, not separate access control.

## Phone interaction

Long-press/select text, adjust handles, then tap the small speech-bubble icon immediately right of the bottom-right-most rendered selection line. The icon is 24 px on desktop with a 4 px gap and centered on the line; touch uses 28 px with a 14 px gap to clear selection handles. It flips left/down only for viewport overflow or a detectable fixed/absolute overlay. It stays absent during mouse drags and appears after release. Touch waits for 350 ms without selection changes on first appearance; once visible, it follows overlapping handle adjustments once per animation frame instead of disappearing. Hit testing pauses while the handles move and always resumes after 350 ms of quiet, even if iOS omits a touchend. When touch events cannot distinguish a handle from a long press, prefer following; a disjoint range starts a fresh selection with the initial delay. Scrolling or a collapsed selection hides it. Keyboard selections debounce for 140 ms after key release. Hiding synchronously disables hit testing before removal. It preserves the native selection callout and does not intercept document touch gestures. The compact composer focuses synchronously inside that tap, allowing iOS to open its keyboard without another field tap. Type and send with the icon. On desktop, Enter or Cmd/Ctrl+Enter sends and Shift+Enter inserts a newline; mobile Return inserts a newline. Composition/IME Enter never submits prematurely.

Subtle highlights open existing threads with a focused reply. Resolve/reopen/close use icons. A comments icon and open-count badge live in the existing toolbar; the list can include resolved and outdated threads. Desktop uses a small selection-adjacent popover; phones use a compact bottom sheet above the visual viewport's keyboard boundary. Both follow the page's dark mode. A native dialog manages focus/dismissal. The [selectionchange event](https://developer.mozilla.org/en-US/docs/Web/API/Document/selectionchange_event) tracks handle adjustments. There is no mode toggle, persistent instruction panel or additional UI dependency. Comments reload after local revision changes or opening the list, but a newer server snapshot never replaces the viewed content automatically. A five-button toolbar shows Home, Share, Comments, Edit and More in one row. Share contains the existing persistent-link toggle and Copy link (available while persistent is on); More pairs icons with Search, Copy text, Change key and the existing two-click Delete confirmation. Native popovers support outside tap, Escape and keyboard focus; arrow keys move between their actions.

Before: enable mode → select → bottom button → focus field → type → post (6 steps). After: select → nearby icon → type → send (4 steps). Automated iPhone-sized WebKit tests use touch taps and verify focus without clicking the input; actual iOS keyboard/callout behavior still needs a physical phone trial.

## Update nudge

`GET /api/revision` reads only the namespaced hash's `rev` field in one Redis command and returns `{rev}` with no-store/noindex headers; a missing or legacy note returns zero. The reader checks while visible, every 20 seconds, backing off to 60 seconds after three unchanged responses (or errors). Hiding the document clears the timer and aborts an in-flight check. Visibility return and window focus trigger an immediate check. No content is fetched by polling.

A higher server revision shows a small “Updated · tap to refresh” pill. Only tapping it refreshes content and comments in place. The pill is deferred while editing or a comment dialog is open; drafts and selections remain intact. Successful own writes advance the local revision and do not nudge. This detects greater revisions only: deletion/recreation at a lower revision is not a notification. A renamed key remains a new address, as before.

## API

Use the origin of the supplied note link, especially for staging. Never substitute the production origin for a Preview link.

- `GET /api/comments?key=KEY&status=open` (default open; also resolved/all) returns `{rev, content, comments}` in one snapshot. Each thread includes its original `anchor`, `created_rev`, `resolved`, `messages`, and current `location` (`attached` with raw source `start`, `end`, `text`, or `outdated` with `text:null`).
- `POST /api/comments` takes `{key, if_rev, operations, content?}`. Operations are `{action:"create",start,end,text}`, `{action:"reply",id,text}`, `{action:"resolve",id}` or `{action:"reopen",id}`; 1–50 per request. Create offsets address the content from `if_rev`, before any replacement content in that request.
- Example agent flow: GET open comments; review current source and original/current quotes; POST a revised `content` and operations `[{action:"reply",id,text:"Updated that section."},{action:"resolve",id}]` with that `if_rev`. GET again to verify. If a thread is outdated, read its original quote and conversation before acting.
- Error statuses: 400 invalid input/limits, 404 missing note, 409 revision race, 413 oversized request/content. All comments responses use no-store and noindex headers. Existing `/api/content` remains compatible.

## Rejected alternatives

- Untransformed offsets alone: edits before a selection move the anchor silently; offsets now transform on writes and verify the exact quote.
- Fuzzy/LLM re-anchoring: guesses can attach a request to the wrong passage.
- Rendered quote search directly in raw Markdown: fails across formatting, links and escaping.
- Separate Redis comments key: adds cross-key expiry, rename and delete failure modes without a prototype benefit.
- Independent comment revisions: less contention, but more conflict contracts for atomic edit-and-resolve.
- Accounts, permissions, notifications, CRDTs, history and a rich editor: expand this focused trial into a different product.
- Hide comments from key-bearing persist visitors as “private”: cannot enforce that with the existing bearer credential.

## Approved decisions and remaining limits

Lawrence approved comments being readable by every bearer-link holder and exact-quote anchoring with the Outdated fallback. You/Agent roles and the staging trial are also decided. Merge/deploy to production still requires separate review.

Known limits: no authenticated identity, no per-thread delete/edit, no manual reattachment, no history/undo, no notifications, no actual iPhone keyboard/callout evidence yet, shared-demo contention, and Preview API calls blocked by Vercel protection unless the caller already has authorized access.

## Tap-to-select preview trial

Preview builds add double-tap selection on coarse-pointer devices and double-click selection on desktop; a single mobile tap does not start auto-selection. The viewer uses `touch-action: manipulation` so double tap does not invoke browser zoom while pan and pinch remain available. Links, controls, and thread marks keep their own tap behavior. The client generates deduplicated raw-Markdown spans around the hit word (word, directional noun/verb-sized phrases around it, punctuation-bounded clause, sentence, and line/list item/heading where distinct), then shows the ranked top pick as a native selection beside the existing comment bubble. The −/+ chips move one distinct span size smaller/larger per tap, using rank to break equal-size ties. The bubble opens the unchanged composer and stores the selected raw source offsets. Existing drag selection and long-press handle adjustments still use their original path.

The small `Tap select` control in view mode switches Jev and heuristic; `&tap=jev` or `&tap=heuristic` in the Preview URL makes the comparison repeatable. A source and latency label appears by the bubble. The adjacent `Jev wait` control compares `&tapwait=200` with `&tapwait=700` (the default). The route and UI are hard-gated on `VERCEL_ENV=preview`; production remains off even if `TYPESAFE_API_KEY` exists there. Add `TYPESAFE_API_KEY` to the Vercel **Preview** environment and redeploy the branch for live ranking. A missing key, timeout at 800 ms, invalid answer, or service error uses a focused phrase when a clause runs long, falling back to the smallest available phrase if none has clean boundaries; a short complete clause stays intact. Clause candidates now stop at sentence punctuation as well as commas and dashes. A small spinner appears with no selected text for at least 200 ms. After that, a ready response settles the one selection immediately, or the heuristic settles at the chosen 200/700 ms cap; Heuristic mode keeps the 200 ms wait. A late reply can update timing text but never changes the displayed quote. The client aborts an outstanding diagnostic request if another gesture supersedes it, the composer opens, or the request reaches 1.5 seconds. Jev is guided toward the shortest meaningful phrase or words carrying the comment target; when Jev only modestly prefers a long clause or sentence over a plausible phrase (less than a fourfold lead), that phrase becomes first and the source label says `jev · focused`. A decisive broad choice stays first. A full sentence remains a candidate when its wider claim or contrast is necessary and is reachable with +.

Only a capped nearby passage (at most 2,200 UTF-16 characters, about two sentences each way) and up to 15 candidate quotes reach the Preview route; the route caps the entire body at 8 KiB and sends no note key, full note, comments, or credentials to TypeSafe. It logs no content. TypeSafe receives one Choice request pinned to `jev-1.13.0`, with neutral labels in a deterministic length-independent order. The response's token usage and estimated input-token cost are returned to the Preview client when present. The Preview route requests Vercel's `sfo1` region to put this single call nearer TypeSafe's currently West Coast service; actual deployed region must be checked from the Preview label and any latency gain measured there. The response returns numeric route and TypeSafe durations, a fixed outcome code, and the validated region when Vercel supplies one. The small label shows the source, gesture-to-selection time, server durations, approximate time outside the route, or the cap and late-response timing. The outside-route value includes transport, platform scheduling/cold start, and client work, so it cannot identify one cause alone. These values contain no note text or key. TypeSafe currently lists $0.042 per million input tokens and free output tokens, so a 1,000-input-token call is about $0.000042; actual usage and end-to-end latency need an authorized live Preview trial. The revised Jev instruction is 156 characters and 25 whitespace-delimited words longer than the previous instruction; the actual token delta and any effect on live latency are unknown. A client abort may not cancel work already accepted upstream, so a late response can still incur usage even when the heuristic is displayed.

This is a line-oriented prototype: clause splitting is punctuation-based rather than grammatical, and CJK segmentation depends on `Intl.Segmenter`. Links and common inline formatting are kept whole when candidate boundaries intersect them. The existing renderer still cannot map partial selections through decoded entities or unpositioned fenced code. Native iOS callout and keyboard behavior need a physical-device trial; automated iPhone-sized WebKit covers DOM touch behavior only.
